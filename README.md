# Aurora386

An Intel 80386 PC emulator written in C#, built to be read as much as to be
run. Every device is modelled the way the real silicon behaved, and the
comments explain *why* the hardware works that way — not just what the code
does.

It boots MS-DOS 6.22 from the original installation floppies.

## Status

**CPU accuracy: 99.99%** — 1,758,490 of 1,758,700 tests from
[SingleStepTests/80386](https://github.com/SingleStepTests/80386), a suite
generated by driving a real 386EX through its pins and recording every bus
cycle. The remaining failures are cases where the hardware itself is not
deterministic: undefined flags after `AAM 0` and after a division overflow,
and one port whose idle value depends on the board.

**MS-DOS 6.22** installs from the four original floppies and boots from the
hard disk to an interactive `C:\>` prompt, with HIMEM.SYS loaded and the
extended memory scan completing.

## What is emulated

| Component | State |
|---|---|
| 80386 CPU, real mode | Complete |
| 80386 CPU, protected mode | Descriptors, interrupt and trap gates, IRET |
| Memory bus, A20 gate, unreal mode | Complete |
| 8259 interrupt controllers (master + slave) | Complete |
| 8253 programmable interval timer | Complete |
| 8237 DMA controller | Complete |
| 8042 keyboard controller | Complete |
| CMOS / real-time clock | Complete |
| VGA text modes | Complete, including 40-column and 43/50-row |
| VGA graphics modes | 0Dh, 0Eh, 10h, 12h planar; 13h with DAC palette |
| BIOS services (disk, video, keyboard, system) | Complete for DOS |
| XMS memory manager | Complete |
| Floppy and hard disk images | Complete, with media change detection |
| CD-ROM (ISO 9660) | Image reading; no MSCDEX driver yet |
| Sound Blaster 16 + OPL3 | DSP, mixer, DMA playback, FM synthesis |
| NE2000 Ethernet | Registers, ring buffer, remote DMA; loopback backend |
| Virtual 8086 mode, TSS, paging | Not yet |

## Building

Requires the .NET 10 SDK.

```
dotnet build -c Release
dotnet test tests/Aurora386.Tests -c Release
```

## Running

The graphical front end is the one to use. It has a toolbar, drive activity
lights, a file browser for swapping disks while the guest is running, and a
step-by-step debugger:

```
dotnet run --project src/Aurora386.Gui
```

There is also a minimal SDL front end for running headless:

```
dotnet run --project src/Aurora386.Sdl -- --floppy disk.img
dotnet run --project src/Aurora386.Sdl -- --hdd hdd.img
dotnet run --project src/Aurora386.Sdl -- --help
```

Disk images are not included: they are large and generally covered by
copyright. Point the emulator at your own.

## Installing MS-DOS

Create a disk, then boot the first installation floppy with it attached:

```
dotnet run --project src/Aurora386.Sdl -- --create-hdd hdd.img --size 200
dotnet run --project src/Aurora386.Gui
```

In the GUI, attach `hdd.img` as the hard disk and the first floppy as drive
A:, then press Start. When setup asks for the next disk, use the *Floppy A…*
button to swap the image: the BIOS reports the media change through its
change line, so DOS notices the new disk rather than trusting what it read
from the last one.

## Design notes

**An interpreter, not a JIT.** The goal is a machine you can read and step
through, so the CPU is a straightforward decode-and-execute loop. It is fast
enough to run DOS comfortably.

**The core is headless.** `Aurora386.Core` has no display or input
dependency: it exposes a framebuffer and accepts scancodes. That makes the
whole machine testable without a window, which is how the 163 project tests
run in under half a second.

**Lazy flags.** The x86 flag register is expensive to maintain and rarely
read. The CPU records the operands and the operation, and materialises the
flags only when something actually looks at them.

## Some things the hardware does that surprise people

These are all real behaviours, discovered by testing against hardware traces
and documented in the source where they matter:

- **Scaled index with no index register.** In the SIB byte, when the index
  field says "none", the 386 still applies the scale factor to the *base*
  register. Later processors dropped this.
- **Unreal mode.** Returning from protected mode to real mode recomputes only
  the segment *base*. The *limit* survives in the descriptor cache — which is
  exactly how HIMEM.SYS reaches memory above 1 MB using ordinary
  instructions.
- **`INC` and `DEC` inherit the carry flag** rather than computing it, which
  is what lets them appear inside multi-precision addition loops without
  destroying the running carry.
- **A word access that crosses a segment limit faults** — it does not wrap.
  But a 32-bit *stack pop* on a 16-bit stack splits into two word accesses
  that each wrap independently.
