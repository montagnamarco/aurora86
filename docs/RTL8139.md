# RTL8139(C) PCI Fast Ethernet

The optional `rtl8139-pci` card models Realtek's 1997 RTL8139(C), the card
an in-box Windows 98SE/2000/XP driver or a Linux `8139too` kernel finds
already fitted. Unlike `rtl8029-pci`, this is not the DP8390 core behind a
PCI BAR: it is its own bus-mastering register engine, reading and writing
guest RAM directly for both its transmit descriptors and its receive ring.
Select it in the existing `hardware.network` entry in `vm.json`:

```json
{"card": "rtl8139-pci", "port": "C200", "mode": "none"}
```

The card occupies PCI 00:05.0 -- the same slot `rtl8029-pci` uses, since
this machine has one physical PCI network slot and the two cards are
alternatives for it, never both fitted at once -- and identifies as
10EC:8139, class 020000h, revision 10h (the value 8139too's own chip table
expects for an "8139C" step; the 8139C datasheet's PDF text layer could not
be extracted, so this is taken as given rather than independently
re-derived). PCI INTA uses PIRQD, routed by the motherboard.

## BAR0 (I/O) and BAR1 (memory)

BAR0 is a 256-byte I/O window, the real chip's own size. Its default port is
C200h unless configured otherwise -- **not** 300h, the NE2000's traditional
address: 256 bytes at 300h would swallow half of the VGA CRTC/DAC/sequencer
ports (3C0h-3DFh), the IDE control block (3F6h) and COM1 (3F8h), none of
which a real PCI BIOS would ever place a BAR on top of. C200h is clear of
every fixed port this machine has: the bus-master IDE engine at C000h and
both UHCI controllers at C100h/C120h.

BAR1 is sized to 4 KB rather than the real chip's 256 bytes.
`PhysicalMemoryBus.TryMapDevice` only ever places a device on a 4 KB page
boundary, for a length that is itself a multiple of 4 KB; the real 256-byte
BAR1 cannot decode on this bus at all. Both BARs answer the identical
register file -- writing a register through one and reading it back through
the other sees the same value -- but only offsets 000h-0FFh of the memory
BAR actually decode anything; 100h-FFFh of it read as an empty bus, exactly
as the real 256-byte decode would past its own end.

## Registers modelled

IDR0-5 (loaded from a synthetic locally-administered MAC at every reset,
read-only otherwise), MAR0-7 (plain storage, no hash filtering -- the same
simplification the NE2000 core already makes for multicast), TSD0-3/TSAD0-3
with OWN/TOK, RBSTART, CR (RST self-clearing, TE, RE, and a computed BUFE),
CAPR/CBR, IMR/ISR (write-1-to-clear, RxOK=0/RxErr=1/TxOK=2/TxErr=3 as in
Linux 8139too and QEMU's `rtl8139.c`), TCR (stored, not interpreted: this
model has no CRC or interframe-gap timing to gate), RCR (AAP/APM/AM/AB
filters, WRAP, RBLEN ring sizing), 9346CR (gates CONFIG0/1/3/4 writes and
synchronously reloads the synthetic MAC on "auto-load" -- no serial EEPROM
bit-bang protocol, the same simplification `rtl8029-pci` already makes for
its own 93C46), CONFIG0/1/3/4 (read-back storage only; no LWAKE/FUDUP/sleep
behaviour), MSR (fixed: link up, 100 Mb, no pause), BMCR/BMSR (fixed
capability: 100 Mb full duplex, auto-negotiation always complete -- there is
no real link partner to negotiate against), and ANAR/ANLPAR/ANER (plain
storage). The missed-packet counter, the free-running timer and its compare
register, and the early-receive threshold registers are not modelled: no
driver depends on them, and adding them would mean guessing an unverified
register offset.

## Receive ring

The ring lives in host RAM at RBSTART, reached only through
`PciBus.DmaMemory` and only while the PCI command register's bus-master bit
is set -- clearing it stops both directions of DMA at once, exactly as
`PciFunction.BusMasterEnabled`'s own contract requires. Each delivered frame
is a 4-byte header (16-bit status, 16-bit length counting the 4-byte wire
CRC this emulator's `INetworkBackend` abstraction already stripped) followed
by the frame, padded to a whole number of four-byte words. CAPR is the
driver's own read cursor, offset by -16 by the driver's own convention (a
freshly reset ring therefore reads CAPR back as FFF0h); CBR is the chip's
own write cursor, never offset. A frame that would not fit in the space
between them sets ISR's RXOVW bit and is dropped whole -- nothing is ever
written past the space the driver has freed, matching the receive-overflow
test case. With RCR's WRAP bit set, a frame that would straddle the ring's
nominal end is allowed to spill into 1500 extra bytes past it instead of
being physically split; the next frame's cursor still wraps to ring offset
zero exactly as if WRAP were clear.

## Transmit

Four independent descriptor slots exist so a driver can queue several
frames without waiting for each one. This model has no transmit timing: the
moment a slot's OWN bit is cleared with a non-zero size, that slot is
fetched from guest RAM and handed to the backend synchronously, then OWN is
set again and TOK raised. There is no enforced ordering across the four
slots and no early-transmit-underrun model: fetch-then-send. Clearing the
bus-master bit while a
descriptor's OWN is already cleared leaves it exactly as the driver wrote
it; re-enabling bus mastering later does not retroactively fire it; the
driver must rewrite the descriptor.

## Snapshot

State is captured under a new `R139` section, versioned and length-checked
through `CardCatalog.NewestSnapshotVersions`/`FixedSnapshotLengths` exactly
as every other card's section is -- an old snapshot with no `R139` section
restores a machine with the card at its power-on defaults, unaffected. PCI
configuration (both BARs, the command register) is captured separately by
the machine's own PCI section. The backend is host state with no guest
counterpart and is not captured, the same reasoning `Ne2000`'s own summary
gives. Restoring a mid-reception/mid-transmission snapshot does not itself
replay any DMA: the register file (including the receive write cursor and
the transmit descriptors) comes back exactly as captured, but the bytes a
transmit or receive already moved into RAM before the snapshot was taken are
whatever that RAM held at capture time, unrelated to the restore itself.

## What is not modelled

Serial EEPROM programming (9346CR only gates configuration-register writes
and a synchronous MAC reload), PCI burst-size and FIFO-threshold timing, the
missed-packet counter, the free-running timer, and real Windows/Linux driver
compatibility beyond the register contract above -- no in-box driver has
been run against this card.
