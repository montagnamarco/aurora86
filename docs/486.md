# What the 486 adds, and what of it is here

Aurora386 boots as a 486 by default and can be told to be a 386
(`CpuModel` in `vm.json`, the *CPU* menu in the window). The difference is
small and precise, and it matters because software tells the two apart and
behaves differently on each. This is the list of what the emulated 486
does beyond the 386, and of what it does not pretend to do.

## Instructions

| Instruction | Opcode | Notes |
|---|---|---|
| `BSWAP r32` | 0F C8+r | Reverses the four bytes of a register |
| `CMPXCHG r/m, r` | 0F B0 / 0F B1 | Compare with the accumulator, exchange on equality; ZF says which |
| `XADD r/m, r` | 0F C0 / 0F C1 | Exchange and add, the primitive behind atomic counters |
| `INVLPG m` | 0F 01 /7 | Drops one page's cached translation from the TLB |
| `INVD`, `WBINVD` | 0F 08, 0F 09 | Privileged, and otherwise do nothing: there is no cache to flush |
| `CPUID` | 0F A2 | See below |

On a 386 every one of them raises #UD, which is what programs written
before 1989 expect and what a few identification routines rely on.

## Identification

Two things tell software which processor this is, before it ever asks.

**EDX after reset** holds the family, model and stepping: 0x0480 for the
486 (family 4, model 8, a DX4), 0x0308 for the 386. **The AC flag** (bit
18 of EFLAGS) can be set only on a 486; a program that pushes the flags,
flips that bit, pops them and reads them back learns the model without any
new instruction, and that is how Windows 95's setup checks. On a 386 the
bit stays clear.

`CPUID` answers function 0 with the highest function supported (1) and
"GenuineIntel", and function 1 with the same signature as EDX and one
feature bit: an on-chip floating point unit. Nothing else is claimed --
no time stamp counter, no page size extensions -- because nothing else is
there.

## Control registers

The 486 gave CR0 bits the 386 did not have, and two of them change how the
machine behaves:

- **WP (bit 16), write protect.** With it set, a page marked read-only for
  user code is read-only for the kernel too. The 386 ignored the read-only
  bit at ring 0; the 486 honours it when WP is on. The protected-mode
  hardware suite assumes WP, and the emulator implements it, which is
  harmless to Windows 3.11 (it never sets the bit).
- **AM (bit 18), alignment mask,** with AC in EFLAGS: an unaligned access
  at ring 3 raises #AC (vector 17) when both are set. Implemented for
  reads and writes of words and doublewords.
- **ET (bit 4), extension type,** reads back set on a 486, whose
  coprocessor is the built-in kind, and clear on a 386.
- **NE (bit 5)**, numeric error: accepted and stored. The coprocessor is
  a software one (`Firmware/Fpu`), reached through the "device not
  available" fault, so the difference between an IRQ 13 and a #MF
  exception never arises.
- **CD and NW (bits 30, 29)**: accepted; there is no cache to disable.

The reserved bits and the bits the model does not have are masked on
write (`CpuState.Cr0Writable`), so a 386 cannot be tricked into WP by
writing it.

## Debug-register aliases

On both supported CPU models, MOV to or from DR4 accesses DR6, and DR5
accesses DR7. Both names refer to the same stored value; they are not
independent registers. The existing supervisor check still applies.
`Intel486InstructionTests.DebugRegisterAliasesShareStorageInBothDirections`
executes writes and reads through both names on the 386 and 486 models.
See Intel's [debug-register compatibility rules](https://www.intel.com/content/dam/www/public/us/en/documents/manuals/64-ia-32-architectures-software-developer-system-programming-manual-325384.pdf),
section “Debug Registers DR4 and DR5”. Breakpoint triggering remains
separate from register access and is not implemented by this change.

## What is deliberately not there

- **Cache behaviour.** No lines, no write-back; INVD and WBINVD are
  privilege checks. Software cannot observe a cache except through timing.
- **Prefetch and self-modifying code differences.** The 486's longer
  prefetch queue makes some self-modifying code behave differently from
  the 386; the emulator executes what is in memory at the time, which is
  the 486's behaviour after a jump and the 386's always.
- **Timing.** Instructions take one emulated cycle each. Nothing depends
  on the 486's clock-doubled DX2/DX4 arithmetic, and the 8253 timer keeps
  time on its own.

## How to check it

`Intel486InstructionTests` covers BSWAP, CMPXCHG, XADD and the model gate
that turns them into #UD on a 386; CPUID and the CR0 masking are exercised
by the same class and by `CpuTests`. The protected-mode hardware suite
(`tools/HardwareSuite`) passes 6100 of 6100 with the default 486 model;
it was captured on hardware that honours WP, and so does the emulator.
